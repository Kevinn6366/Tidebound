## 1. 项目定位与共同原则

### 1.1 产品定位｜已确认

> 这是一个以长期关系为核心、由事件驱动、能够调用工具行动的角色陪伴系统。Galgame 是交互呈现，亚托莉是首个角色实现。

系统面向持续的陪伴关系，而不是以推进预设剧情为唯一目标。角色具有人格与表现风格，能够感知时间，并通过工具了解现实世界。首个角色参考亚托莉；长期目标是通过符合项目标准的角色提示词 bundle 兼容其他角色，而不是将亚托莉的设定写死在运行时内核。

kevin6366 使用“虚拟世界的陪伴者”描述角色的存在形式，同时认可“不做独立世界模拟器”。本文据此记录为：**角色以虚拟形象存在，能够接触现实世界的信息，但 V1 不建设独立运行的世界模拟系统。**这不意味着需要实现虚拟地理、经济、作息或剧情世界的完整状态模拟。

### 1.2 三项基本共识｜已确认

长期运行不等于模型一直思考。单一 session 不等于无限增长的模型上下文。会话回退不等于撤销现实世界。

其中，**严格控制模型上下文**与**可靠保存长期记忆**被明确指定为后续重点讨论的两个独立模块。本轮确认其重要性，不提前敲定压缩、检索、摘要更新或记忆分层算法。

### 1.3 工程原则｜已确认

采用敏捷开发与最小可行迭代。当前阶段不引入无实际需求的分布式基础设施，不为未来能力提前堆叠技术栈。

所有 Agent 相关业务逻辑使用 Python 重写，自行组织运行循环与状态管理，不使用 LangChain 一类 Agent 框架承载核心运行逻辑。“手写 runtime”并不等于自行重写 HTTP、数据库驱动或其他通用基础库。

采用 spec 驱动开发，以普通仓库文件承载约束与规格。参考 DeepSeek Harness 的开发组织思路，不将接入其运行时或引入大型 harness 平台作为项目要求。

## 2. 命名：Tidebound 与 TideTime

### 2.1 项目名称｜已确认，暂定使用

**中文名：汐伴。英文名：Tidebound。**

这是整个产品与项目的名字，不限定某一个角色，也不等同于某一轮聊天。

### 2.2 Runtime 名称｜本轮命名，具体语义待细化

**TideTime（汐时）**，作为此前 `xxtime` 占位名的替代名称。

该名字由 gpt6astra-pro 应 kevin6366 的命名请求提出并用于本记录：`Tide` 与 Tidebound 的海潮意象呼应，`Time` 指角色与用户共同度过的时间，以及系统被唤醒后的活跃执行阶段。此处确定讨论用名，不表示生命周期设计已经完成。

**TideTime 是 Tidebound 自研 Agent Runtime 的专有名称。**按照 kevin6366 的构想，Agent 的思考、工具调用、工作流交互，以及未来的多 Agent 协作，都在这一运行时范围内发生。讨论中的“一次 TideTime”暂指一次活跃执行阶段；这一阶段结束后，交互侧返回等待用户输入的状态。

“TideTime 阶段结束”不表示长期 session 被关闭，也不表示服务器进程退出。系统常驻与一次活跃执行的结束，是不同层面的生命周期。

### 2.3 与现有术语的关系

| 术语 | 本轮认可或采用的含义 | 尚未冻结的部分 |
| --- | --- | --- |
| Session | 持续存在的关系历史 | 最终数据结构，以及未来多角色与 session 的绑定方式 |
| Run | 一次有限的执行 | 是以单个 Agent 为单位，还是与一次 TideTime 对齐 |
| Context | 某次模型调用实际可见的材料 | 构建、预算、压缩、裁剪与记忆装配策略 |
| TideTime | 自研运行时的专名；其活跃阶段容纳 Agent 的执行活动 | 与 Run 的数量关系、起止条件、后台工作的归属与跨阶段行为 |
| Workflow | 由代码规定执行过程的工作流，可包含模型调用 | 触发协议、等待方式、取消与结果提交协议 |

后续需要讨论：一次 TideTime 是否包含多个 Run；记忆整理是否可以跨越 TideTime 结束点；人工或定时事件是否开启新的活跃阶段；未来多个 Agent 如何共享或隔离状态。

**本轮不要求回答这些问题，也不因为引入名称就新增一套数据库实体或调度抽象。**

## 3. RQ1：角色存在方式与产品范围

**状态：已确认。**

V1 做具有角色人格、能够陪伴用户并通过工具了解现实世界的虚拟角色，不做独立世界模拟器。角色知道时间，并可以获得现实世界发生的事情，而不局限于模型已有知识。

现实信息获取能力通过工具提供。工具实现集中放在 `src/tools/`。角色是否、何时主动获取信息，以及由什么事件唤醒，留待工作流与 TideTime 生命周期讨论。

长期关系、人格一致性、共同经历的保留是产品主线；Galgame 是用户交互的呈现形式，不应反过来要求所有业务都按照剧情分支或游戏存档槽建模。

## 6. RQ4：长期 session、管理员回退与旧结果隔离

### 6.1 Session 语义｜已确认

一个陪伴实例对应一个长期逻辑 session，内部允许保留历史版本或分支，始终只有一条活动时间线。这里的“单一 session”是用户或陪伴实例范围内的约束，不是整个多用户服务共享同一个 session。

普通用户没有手动切换 session 的入口，也不能任意回退已完成的历史。管理员可通过后台 console 管理、切换和调试 session，并执行历史回退。

V1 的回退目标限定为已经提交的对话轮次，不实现任意 token 级回退。历史版本和分支采用什么数据结构，尚未决定。

### 6.2 回退范围｜已确认，必须保留

管理员执行回退时，不得只隐藏后续聊天文本。必须一起处理与目标状态相关的记忆快照、角色状态，以及尚未执行的派生任务。

**任何基于旧活动时间线启动的工作，即使在回退后才执行完成，也不得把结果提交到新的活动时间线。**

这一约束适用于主 Agent 回复、工具结果的会话写入、摘要写入及其他工作流产物。是否保留这些迟到结果作为日志，是另一回事；“可以审计”不能等同于“允许进入当前上下文”。

例如，系统已在第 25 轮生成包含第 20 轮信息的摘要，管理员回退到第 15 轮后，当前模型不得继续读取该摘要中的未来信息。相同要求也适用于回退前已经启动、回退后才生成完成的摘要。

历史关联标识、状态版本校验及具体提交机制待设计。本轮确认结果有效性的语义，不指定某一种锁、版本字段或事件溯源框架。

### 6.3 外部副作用｜已确认

已经完成的现实世界操作不随 session 回退而自动撤销，也不得因为历史重放再次执行。V1 按 kevin6366 的意见，将这些操作记录在日志中，不另行建设完整补偿系统。

日志的格式、持久化位置、保留期限，以及如何为后续重放提供去重依据尚未敲定。**整理说明：记录日志不等于已经实现撤销或防重复执行；外部动作完成后的审计与重放规则需要在实现该能力时写入 spec。**

## 7. RQ5：手写 runtime、主 Agent 与停止操作

### 7.1 “手写”的准确含义｜已确认

手写 runtime 指开发中不依赖 LangChain 一类 Agent 框架，自行编排 Agent 循环、工具交互、状态提交与工作流衔接。它不表示为了自研而重造所有底层组件。

V1 只有一个具有自主决策权的主 Agent。基本循环包括读取状态、构建上下文、调用模型、处理工具调用，以及继续执行或提交结果。

记忆摘要等工作流可以包含模型调用，但不因此被包装成具有自主规划权的“记忆 Agent”。未来会引入多 Agent 协作，但规划者、执行者、反思者、情绪 Agent 等角色分工不进入 V1。

调度、权限、写入顺序、终止条件、重试策略与 token 预算由代码控制。同一条活动时间线的状态提交需要串行化；这不是要求不同用户之间也共用一把全局执行锁。

### 7.2 用户输入策略｜已确认

当前不允许用户在一次执行尚未结束时连续发送消息。不以排队、合并新消息或自动打断作为 V1 的默认行为。

用户可以手动停止当前执行。按本轮要求，停止后回到上一个状态。**“上一个状态”的精确边界仍需定义**：例如，刚提交的用户消息是否保留在正式历史中，尚未生成完的回复如何记录，均不能由本次整理擅自决定。

### 7.3 用户停止与管理员历史回退的区别｜已确认的行为区分

| 操作 | 发起者 | 作用范围 | 本轮要求 |
| --- | --- | --- | --- |
| 停止当前执行 | 普通用户 | 当前尚未完成的执行 | 停止后恢复到上一个状态；精确恢复点待定 |
| 回退已提交历史 | 管理员，通过后台 console | 已提交对话及其关联状态 | 同时处理记忆、角色状态和未执行派生任务 |
| 手动切换 session | 管理员，通过后台 console | 不同会话或调试目标 | 普通用户不提供此入口 |

**后续实现需要落实的语义：**停止不能只是停止浏览器展示；取消后迟到的任务结果不能继续改变恢复后的活动状态。具体取消协议，以及如何处理无法中断的外部调用，尚未决定。

普通用户的停止能力，不构成任意回退历史的权限。已经完成的外部副作用仍遵守 RQ4 的记录规则，不因用户停止而被视为不存在。

## 8. RQ6：首批工具、工作区与沙箱

### 8.1 首批工具方向｜已确认

首批工具用于赋予 Agent 了解外部世界的能力，包括互联网访问。工具集中放在 `src/tools/`。具体搜索、网页读取及其他信息来源的清单与供应商待定。

Agent 的 `cwd` 必须明确，不能任意游走或修改系统中的其他位置。沙箱的主要保护目标是关键数据不被越权修改，以及执行范围受到实际约束。

### 8.2 隔离要求｜原则已确认，实现待讨论

不将普通子进程加路径检查称为完整沙箱。若存在生成代码的执行或命令执行，需要有真实的隔离执行环境，并约束工作目录、网络、资源与运行时长，不暴露宿主凭据或 Docker socket。

**整理说明：**固定 `cwd` 是工作区约定，不单独构成权限隔离；用于部署 Web 服务的 Docker 容器，也不能自动被认定为已满足执行不可信代码的沙箱要求。这两类隔离应分别验证。

由于 Dev 要支持 Windows、macOS、Linux，Prod 使用 Linux Docker，沙箱的跨平台开发方式仍需专门讨论。本轮不选择具体沙箱产品，不预设每种宿主都能以相同方式原生隔离。

### 8.3 Python 代码生成｜首批期望，采用工作流方向

kevin6366 希望加入 Python 代码生成，但通过工作流实现，**不封装成主 Agent 可以任意生成并执行代码的通用工具**。其目的在于控制生成与执行范围，避免随意写代码、随意运行。

是否执行生成的代码、是否需要人工批准、使用何种检查与隔离步骤、允许访问哪些数据，尚未决定。不得把“希望加入 Python 代码生成”直接解释为“V1 已授权自动执行所有生成代码”。

工作流如何被 Agent 请求，亦不在此处预先规定为某个 function-calling 工具。工作流调用接口与代码执行权限是两个需要分别讨论的问题。

## 9. RQ7：工作流、触发来源与结果返回

### 9.1 工作流职责｜已确认

工作流是执行过程由代码约束的流程，可以由确定性事件或人为设置触发。读取哪些输入、经过哪些步骤，以及如何交还结果，应有明确的代码规则。

V1 明确需要的工作流是 **记忆整理 summary**。Python 代码生成也按工作流方向规划，其具体执行边界尚未敲定。除此之外，不为了扩展性提前建设大量工作流类型。

### 9.2 Agent 触发工作流｜当前明确倾向，协议待讨论

kevin6366 提出的期望交互是：

> Agent 判断当前事件需要进入某个工作流，提出触发请求；工作流执行后，将结果返回给 Agent，由 Agent 继续处理。

本轮将其记录为需要支持的方向，但不提前固定调用协议、同步或异步方式，以及它是否完全覆盖记忆整理的触发模式。

**整理说明：**Agent 判断“需要做什么”与代码控制“获准后怎样执行”可以分开。前者可以包含模型判断，后者仍采用固定的工作流规则。因此，不应将“确定性工作流”误解为所有触发意图都必须由固定阈值产生，也不应据此允许模型任意修改工作流步骤。

工作流包含模型调用时，流程规则明确不等于每次生成内容逐字一致。

### 9.3 尚未决定的触发与生命周期问题

记忆 summary 由固定阈值、定时事件、人工配置还是 Agent 请求触发，以及这些方式是否组合使用，尚未敲定。

工作流是否阻塞当前 TideTime、后台摘要能否在交互进入等待状态后继续运行、结果如何关联原来的输入快照、取消与历史回退如何影响执行中的工作流，都需继续讨论。

无论最终选择哪种调度方式，工作流不得绕过 RQ4 中“旧时间线的结果不能污染新时间线”的要求。

## 10. RQ8：上下文、持久化与长期记忆

**状态：总体目标与部分初始选择明确；具体架构待重点讨论。**

从初始需求沿用的选择是：当前采用 MySQL；全部对话需要持久化；长期记忆先走后台工作流生成 summary 的简单路线。

kevin6366 本轮再次强调，单一 session 下需要严格控制上下文并可靠保存记忆。长期 session 不要求全部历史永远进入一次模型请求；上下文材料的裁剪与原始历史的保存应分别设计。

本轮尚未决定消息、运行状态、记忆快照与日志分别如何存储，也没有逐项确认上一轮提出的“数据库作为唯一业务事实来源”、具体摘要分层或上下文拼接顺序。因此，本文不把这些候选方案写成冻结设计。

后续需要重点解决：上下文预算如何分配；何时压缩；summary 如何更新及保留来源；摘要有误或遗漏时怎样修正；摘要如何与回退点一致；多用户之间如何隔离；原始历史与摘要分别如何保留。

回退后的记忆一致性已经确认，不能以“先做简单 summary”为由延后处理。具体实现可以最小化，但不能使用已经失效或来自未来时间线的摘要。

不引入未经讨论的向量数据库、RAG 平台或多层自主记忆 Agent。本轮也不对这些能力作永久排除，是否需要由后续场景决定。

## 11. RQ9：提示词 bundle 与角色兼容

**状态：沿用初始明确要求；bundle 标准仍待设计。**

所有提示词集中在 `prompts/` 下管理，以 bundle 形式组织，不允许散落在业务代码各处。主角色提示词使用类似 `chat.main.character` 的逻辑标识；工作流中的提示词同样纳入 bundle 管理。

后续兼容其他角色的路径是提供符合标准的角色提示词 bundle，而不是为每个角色修改 runtime 内核。亚托莉是首个实现，不是内核规则的专有分支。

manifest 格式、模板文件布局、变量定义、版本固定方式、共享规则组织和更新策略尚未敲定。角色包是否进一步包含声音、表情或其他资源引用，也未决定，不能因为这些内容在上一轮 RQ 中出现过就纳入 V1。

`src/tools/` 与 `prompts/` 是本轮已明确的目录约定；完整仓库结构尚未冻结。
