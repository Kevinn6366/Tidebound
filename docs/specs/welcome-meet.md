# 登录问候与对话时间

日期：2026-09-17。单 worker dev 的最小初版，对应 issue #3「事件唤醒与可控主动联系」的登录事件切片，不代表定时提醒或离线推送已完成。

## 已确认行为

登录后进入应用标题页时，前端调用 `POST /api/chat/meet`，后端立即返回并继续后台生成；恢复已有登录态、刷新应用也使用这个幂等入口。普通会话轮询和窗口 focus 只查询，不触发生成。首次有效时间线没有已提交历史时生成首次问候；已有历史时，只有距离最后一次正式对话完成严格超过 30 分钟才生成重逢问候，恰好 30 分钟不生成。

2026-09-22 确认：这里的“登录后”指服务端账号身份校验成功，不需要等待点击 START 进入聊天。服务启动、未登录及身份校验尚未完成时不得提前发起问候。当前时间不预先注入见面事件或提示词，由问候模型自主调用 `get_current_time` 获取；工具按 `TIDEBOUND_TIMEZONE` 返回实时结果。后端时钟只用于冷却、1 小时有效期及执行元数据，不替模型选择时段称呼。

一条欢迎语生成完成后立即原子写入正式历史和后续上下文，不等待用户进入聊天。生成成功不等于送达或已读，本期不记录已读状态。用户进入时，已完成的正文使用现有逐字动画展示；未完成则显示“正在准备问候…”，订阅同一 Run，完成后展示。没有周期性问候定时器。

每个账号、有效时间线独立去重：自最近一次成功的普通对话之后，已成功欢迎从 `completed_at` 起有效 1 小时（旧记录缺失时回退 `created_at`）。不足 1 小时的刷新、多标签页及服务重启均复用；达到 1 小时后，下次登录进入应用检查时重新生成，由该次问候模型按需重新调用时间工具。时间流逝本身、普通轮询和窗口 focus 不触发生成；已有活动欢迎继续复用，不并发重开。过期不删除已提交的历史问候。用户完成新的普通对话后，下一次进入且间隔超过 30 分钟，仍可生成下一条问候。仅查看、失败发送或停止普通对话不重置有效期。

失败、停止、超时或重启中断的欢迎不会进入有效历史，也不会因 1 小时有效期自动重试。页面显示错误并允许继续普通聊天；`POST /api/chat/meet/retry` 提供显式重试，未过期的成功欢迎仍不可重复生成。重试仍检查当前普通执行和有效时间线。

## 执行与提示词

- `RunRecord.kind` 区分 `chat` 与 `meet`，旧记录默认 `chat`。欢迎没有用户正文，成功只提交一条 assistant 消息；事件资料仅进入本次请求审计，不伪造成聊天输入。
- `ChatSession` 负责触发条件、占用账号执行位、停止和时间线检查；普通聊天与欢迎不并发提交。断开 HTTP/SSE 不取消任务，显式停止和清空上下文会撤销旧任务提交资格。
- `src/tidebound/workflows/meet/` 按 `N01-GenerateGreeting.py`、`N02-ValidateGreeting.py` 顺序执行。生成节点复用受控模型—工具循环，仅开放时间查询；模型可自主调用或直接回复，不由程序强制预查。沿用调用次数上限、整轮超时、停止及逐次预算检查。验证正常结束、assistant 类型、非空且不超过 120 字符；不能据此声称已验证句子数量或所有角色语义。
- system 必须包含 `chat.character`、`chat.safety` 和 `chat.meet`。`chat.meet` 正文位于 `prompts/master/chat.meet/chat.meet-zh.md`，只作用于本次问候，不进入下一次主对话的 system。
- 复用现有上下文预算与有效摘要组装，附带见面类型和最后对话时间，不包含当前时间或预计算的时段。模型查询时间后才回填 tool 结果，时间规则只注入紧接着的一次请求。预算不足时复用现有压缩等待，不静默丢弃有效历史。欢迎完成后的普通维护仍按主模型预算调度。见面事件与工具调用链仅进入请求审计，正式历史仍只提交最终 assistant 问候，不将事件伪造成用户输入。
- Console 请求审计使用 `purpose=chat.meet`，可查看实际角色、安全、欢迎规则与历史。页面将该执行显示为“登录问候”。

## 时间规则

用户消息的时间是服务端接收输入的时间。角色回复的 Log 时间改为页面首次开始逐字展示正文时，服务端收到展示确认所记录的 `display_started_at`。后台预生成完成的 `completed_at` 仍独立保留，用于提交审计；未进入聊天时不会提前记录展示时间。展示时间不是已读凭据，存在一次请求的网络延迟。

统一保存 UTC ISO 时间，Log 按服务端 `TIDEBOUND_TIMEZONE` 显示日期和时分。`POST /api/chat/runs/{run_id}/display` 只接收正文版本，不接受客户端时间；按账号、时间线和正文版本校验，首次保存后刷新、多标签页确认都不改写。工具过渡正文撤回时清除其时间，下一段正文重新计时，迟到的旧版本确认会被拒绝。

新回复尚未展示时 Log 时间为空；旧记录没有展示信息则回退到已知完成/创建时间并标记“约”，不把今天查看旧历史的时间写回过去。后台完成即进入有效上下文的规则保持不变。

时间只保存在消息与执行元数据中，不再把 `message_time` 拼进模型收到的对话正文。欢迎事件仅提供上次对话时间；当前时间只能来自本次模型主动请求的时间工具结果；角色输出不应包含内部时间字段或格式残留。

## 模型配置与恢复

`TIDEBOUND_MEET_MODEL` 默认 `glm-5.3-flash`，`TIDEBOUND_MEET_BASE_URL` 和 `TIDEBOUND_MEET_API_KEY` 留空时复用当前主模型服务。欢迎请求采用 low 推理强度，输出预留 1024，独立超时 `TIDEBOUND_MEET_TIMEOUT` 默认 30 秒。凭据仅保留后端；失败不自动切换模型。

复用已有原子 JSON Run 存储，不增加队列或全局账号状态。重启后遗留 running 欢迎标记 interrupted，用户可以显式重试，不自动重放。清空上下文会创建新时间线，旧欢迎与旧对话都不再参与资格判断；该操作本身不触发欢迎，下一次进入应用才重新检查。

## 验证

受控测试覆盖角色与安全注入、首次/重逢、30 分钟边界、持久化去重、后台立即入历史、后续上下文、普通执行冲突、停止/清空/超时迟到结果、失败重试、重启恢复、账号隔离、SSE 终态和旧时间兼容。

浏览器 E2E 使用隔离账号与本地模型协议服务验证“已生成/未生成”两种进入路径、逐字效果、时间 Log、刷新去重及随后普通聊天。2026-09-17 经用户明确授权，另完成一次使用当前配置的 GLM5.3 Flash 首次欢迎真实调用；该单次成功不代表供应商稳定性或全面角色质量评测。

## Dev 工具箱主动测试

管理员可点击“测试欢迎语”，调用 `POST /api/chat/meet/test`。仅 dev 开放，归属固定为自身；主动测试跳过 30 分钟冷却及已完成欢迎去重，便于重复调试。已有活动欢迎则复用，普通聊天执行或清空上下文期间拒绝冲突执行。生成仍使用同一角色、安全与 chat.meet 工作流，正式写入 Log 和后续上下文；该入口不改变自动登录去重规则。
