## 一、文档用途与约束范围

本规格是项目的初期宏观架构基线，供开发者与参与实现的编码 Agent 阅读。它将已经讨论清楚的产品方向、技术边界、运行要求和开发习惯转化为实现约束，并补充项目目录与模块职责。它不是原始聊天记录，也不是已经完成的代码审查、部署报告或测试报告；文中描述的能力是建设目标，不能据此宣称项目已经实现这些能力。

本规格依据 `ARCH-DISC-0001` 和 kevin6366 在本次对话中的补充要求整理。用户明确确认的决定优先于此前提出但未被采纳的建议。本版补充的目录划分、模块职责和运行时工作名属于这份规格的组织约定，不应反写成首次讨论时已经逐项确认的决定。对于仍未敲定的停止检查点、上下文算法、摘要策略、工作流触发协议等问题，本文只约束必须满足的结果，不擅自固定具体实现。

开发 Agent 应当先遵守本文件中的产品范围与跨模块约束，再依据对应功能的专项 spec 编写代码。本文已经确定的目录和职责可以用于建立项目骨架；遇到会改变用户行为、数据语义、权限范围或技术栈的未决问题，应先在专项 spec 中形成明确方案，而不是把个人猜测写成默认行为。宏观规格不要求一次性实现所有模块，也不要求为尚未使用的能力提前创建空框架。

## 二、产品定位与当前范围

Tidebound 是一个以长期关系为核心、由事件驱动、能够调用工具行动的角色陪伴系统。Galgame 是交互呈现方式，不是运行时必须遵守的剧情推进机制。亚托莉是首个角色实现，不是业务内核中的固定身份。系统后续应当能够通过符合项目标准的角色提示词 bundle 接入其他角色，而不为每个角色重新编写运行时。

角色是一个以虚拟身份存在的陪伴者，能够知道时间，并通过获得授权的工具了解现实世界发生的事情。这里的“虚拟世界的陪伴者”不意味着建设一个独立世界模拟器。当前不维护虚拟位置移动、饥饿、工作、经济系统或预设剧情进度等世界模拟机制，也不要求角色持续在后台生成虚构生活。系统关注的是持续身份、共同经历、关系延续和必要的实际行动。

长期运行不等于模型一直思考，单一 session 不等于模型上下文无限增长，回退会话也不等于撤销现实世界。历史保存、长期记忆和本次模型可见上下文是三个不同职责。它们必须配合，但不能用“把所有历史都塞给模型”代替记忆设计，也不能用“上下文已经裁剪”作为丢失历史的理由。

当前主线覆盖 WebApp、文本与角色展示、Python Agent runtime、单主 Agent、长期 session、上下文控制、完整历史与记忆保存、summary 工作流、外部世界访问工具、真实的执行范围约束，以及管理员后台会话管理与回退。Python 代码生成保留为计划中的工作流能力，但是否执行生成结果尚未决定。当前主线的范围不等于已经确定的第一个迭代交付清单。

TTS、口型、动作、语音输入、多 Agent 协作和独立 App 形态都进入 Future，不作为当前主线的实现前提。前端可以保留已存在且不妨碍主线的相关资源或代码，但不能为了让这些功能完整运行，重新引入上游 Agent 业务或扩大本期范围。

当前 v0.01 的实际交付边界以 [Agent loop v0.01](agent-loop-v0.01.md) 为准：固定 atri、单 worker dev、时间工具和本地执行记录。以下 MySQL、多用户、记忆与回退仍是建设目标。

## 三、总体技术路线与部署形态

项目采用单仓库、模块化单体的组织方式。Web 表现层继续基于 GWC-Pro 的前端推进，Agent 相关后端统一使用 Python，FastAPI 承担 WebApp 与后端之间的通信适配。当前数据库采用 MySQL，生产环境部署在 Linux 服务器上，并使用 Docker 容器化。用户通过网址访问 WebApp，后续 App 也应通过服务端接口使用同一套业务能力，而不是复制另一套 Agent 内核。

开发环境以 `dev` 方式启动，服务一个开发用户，要求能够在 Windows、macOS 和 Linux 上进行开发与运行。生产环境以 `prod` 方式启动，面向多个用户。两种环境使用同一套核心业务代码，通过配置切换环境差异，不维护一份本地专用 Agent 实现和另一份生产专用 Agent 实现。开发环境是否使用容器运行 MySQL 或其他必要依赖，仍需在部署专项 spec 中确定。

“模块化单体”表示按照职责划分代码，不意味着每个目录都要独立成为服务。FastAPI 与执行 worker 是否同进程、是否分成少量独立进程，以及应用容器、数据库和执行沙箱怎样组织，尚未敲定。这些选择都应服从单机最小可行部署，不因为需要多个执行单元，就升级为微服务或分布式系统。

本期不引入外部消息总线、分布式调度、分布式锁、独立工作流平台或没有当前需求支撑的通用插件平台。不为了可能出现的未来规模预先加入新的存储系统、向量数据库或任务队列服务。当前不把增加第二套服务端语言可能带来的微小链路差异作为优化目标，也不为了 runtime 另起一套服务端语言。

“手写 runtime”指自行实现 Agent 的执行循环、状态协调和调用控制，不使用 LangChain 等现成 Agent 编排框架。它不意味着禁止使用模型 SDK、HTTP 客户端、数据库驱动、配置加载或测试库等普通依赖。开发组织方式参考 DeepSeek Harness，但不将其直接作为本项目的运行时依赖，也不借此建设一个超出当前产品需要的通用 harness。

## 四、GWC-Pro 复用与前后端边界

项目以 `QiuSui1145/GWC-Pro` 为上游 fork。根据 kevin6366 的说明，上游作者是其朋友，复用事宜已经沟通完成，本规格不再把授权沟通列为阻塞项。该说明记录的是项目方提供的情况，不替代独立的许可审查，也不要求在本阶段重新开展授权讨论。

当前复用范围是 Web 前端与少量通信端代码。通信部分迁入根目录 `webapp/`，Python 业务仍归 `src/`。所有 Agent 相关逻辑必须使用 Python 重新实现，包括 Agent 循环、模型调用编排、会话运行状态、上下文组装、记忆整理调度和工作流执行。代码位于上游前端目录，并不意味着它就属于可直接保留的表现层；其中承担这些业务职责的部分同样需要移除或替换。

前端负责呈现对话、角色和服务端提供的运行状态，接收用户输入、停止请求和必要设置。前端不自行决定模型上下文、不直接管理长期记忆、不持有另一套会话事实，也不绕过新 runtime 调用旧 Agent 接口。模型凭据和具有服务端权限的配置留在后端，不作为角色资源或前端静态文件下发。

FastAPI 负责接收请求、校验输入、识别当前用户及其权限、调用对应应用入口，并将结果与运行状态交给前端。它不承担写在路由函数里的 Agent 推理循环，也不把记忆整理、工具调用和回退逻辑堆在接口处理代码中。普通用户操作与管理员操作必须在服务端区分，不能只依靠隐藏按钮来区分权限。

文本与角色展示是当前交互基础。具体路由、流式协议、重连方式和状态同步格式仍未确定，HTTP 加 SSE 只是此前提出的选项，不是本规格已经选定的通信栈。无论最终采用哪种协议，页面上正在显示的流式内容与服务端已经正式提交的对话都必须能够区分；页面刷新或网络断开也不能自行等同于用户按下停止。重连后的展示和执行恢复规则应在通信专项 spec 中明确。

后台 console 是管理业务会话与执行状态的入口，不只是一个日志窗口。可以在现有 Web 前端中增加管理视图，不要求另建一个后台产品。上游名为 console 的组件是否满足要求，需要根据实际功能判断，不能因为名称相同就视为已经具备管理员回退能力。

## 五、TideTime 与核心运行概念

本规格使用 `TideTime` 作为此前 `xxtime` 的运行时工作名，与 Tidebound 的项目名称保持一致。这是本版对命名请求的补充，不表示其生命周期已经敲定。代码暂时使用通用的 `src/tidebound/runtime/` 目录，不因为采用工作名就立即新增一种数据库实体、独立服务或专有协议。

TideTime 承载的意图是：Agent 在其中思考、调用工具、请求工作流，并在未来容纳多 Agent 协作。一次活跃执行结束后，面向用户的交互进入等待输入的状态。这个名称最终是指整个运行时内核、一次活跃执行阶段，还是一个能够包容多个 Run 的执行空间，仍然保留为专项讨论。现在不能直接把 TideTime、Run、常驻进程和 Session 当成同一个对象。

Session 表示持续存在的关系历史。Run 表示一次有限的执行，它有开始、结束和可识别的结果，而不是一个永远运行的循环。Context 表示某一次模型调用实际看见的材料。同一个长期 Session 会产生多个 Run，同一个 Run 也可以因为工具调用而产生多次模型调用，每次调用使用的 Context 都必须受到控制。

常驻服务和用户可见的活跃执行是不同层次。进入等待输入状态不代表服务关闭，也不能据此推断 summary 等后台维护任务必须全部停止。非用户事件是否可以重新唤起活跃执行、一个 TideTime 是否对应一个或多个 Run，以及多用户之间如何划分这种执行空间，后续再明确。本期只实现单主 Agent 所需的能力，不提前建设多 Agent 总线或协作调度器。

## 六、主 Agent、执行控制与正常交互

V1 只有一种具有自主决策权的主 Agent。它在一次执行中读取当前状态、获取受控上下文、调用模型、处理获准的工具调用或工作流请求，并决定继续执行还是形成结果。这里的“一个主 Agent”是指陪伴实例内的决策主体，不是要求所有生产用户共用一个有状态的全局 Agent。不同用户的历史、执行和工作区必须隔离。

记忆 summary 或代码生成工作流即使调用模型，也不因此成为独立的自主 Agent。本期不建立规划者、执行者、反思者、情绪 Agent 等多角色协作结构。未来可以增加这些能力，但不能让尚不存在的协作协议成为当前单 Agent 实现的依赖。

调度、权限、状态写入顺序、结束条件、重试策略和 token 预算由代码控制。模型可以提出行动请求，但不能通过输出一段文字给自己增加权限、取消预算或修改工作流步骤。runtime 负责把模型的决定转成受约束的执行，而不是无条件执行模型返回的任何内容。

一次普通交互的宏观过程是：通信层确认用户与会话归属，runtime 检查当前是否允许开始新执行，再从存储与记忆模块获取有效状态，通过上下文模块组织模型输入。模型返回结果后，runtime 执行必要的工具或工作流协调，最后在确认执行仍然有效的前提下提交结果，并把状态交回前端。这里描述的是模块协作顺序，不是已经选定的线程、协程或事务实现。

同一活动时间线的状态提交必须串行化。V1 不允许用户在当前主执行尚未结束时连续发送新消息，不实现排队、合并或自动打断策略。前端应限制发送，后端也必须检查，避免同一用户通过多个页面或重复请求同时开启相互冲突的执行。不同用户之间不应因为这个约束而被误做成全站共用一个执行状态。

工作流是否可以与主 Agent 并行运行仍有待细化，但无论怎样运行，都不能绕过当前时间线的写入规则。执行读取的是哪一份状态、结果属于谁、完成后是否仍有提交资格，必须可以判断，不能只凭“这个任务执行成功了”就更新当前会话。

## 七、用户停止与管理员历史回退

用户可以手动停止当前执行，停止后回到“上一个状态”。这个权限只针对当前未结束的执行，不向用户开放任意历史回退，也不意味着用户可以选择已经提交的历史轮次或切换 session。管理员历史回退是另一种独立的管理操作，不能与停止共用一套含义不清的业务行为。

“上一个状态”具体对应哪个检查点仍未确定。停止后是否保留本次用户输入、怎样处理已经显示但尚未提交的文本、已经返回的工具结果放在哪里，以及停止请求与结果提交同时发生时以谁为准，都需要停止专项 spec 明确。在这些问题敲定前，不能把“删掉最后一条消息”“直接清空前端内容”或“结束 HTTP 连接”当成完整实现。

停止必须影响执行的实际提交资格，而不仅是终止页面上的打字效果。某个模型请求或工具调用可能已经无法立即终止，但它在停止后返回的结果不能未经有效性判断重新恢复被取消的执行。未采用的输出可以按审计和历史规则保留，但不能悄悄进入后续有效上下文或长期记忆。具体保存位置和状态字段后续设计。

一个陪伴实例对应一个长期逻辑 session，其内部可以保留历史版本或分支，但始终只有一条活动时间线。普通用户界面不提供手动切换 session 的入口，也不提供自由回退。管理员可以通过 console 管理、切换、查看和调试 session，并将活动时间线回退到已提交的对话轮次。本期不提供 token 级历史回退，也不为了内部版本能力开发用户侧分支浏览器。

管理员回退时，不能只改变聊天列表。对应的记忆快照、角色状态和尚未执行的派生任务也必须得到一致处理。例如用户在第 20 轮透露的信息已经于第 25 轮进入 summary，随后回退到第 15 轮，那么恢复后的模型输入不能继续读到包含这条信息的摘要。恢复可以通过选取有效旧状态或依据允许的历史重建完成，具体采用快照、分支还是其他方式后续确定。

已经读取旧时间线的 Run、summary 或其他工作流，即使稍后执行成功，也不能提交到新的活动时间线。这是跨模块的硬约束，需要同时作用于 runtime、记忆、工作流和存储提交。只在前端隐藏迟到消息不满足要求。实现必须能够判定结果来自哪条时间线，以及在真正写入时它是否仍然有效；具体标识、并发检查和提交协议由专项 spec 决定。

“旧时间线”与“同一时间线又增加了几轮对话”不应混为一谈。summary 可以针对一段已确定的历史生成，但它不能引用回退后已失效的内容，也不能用较旧的结果覆盖更合适的新状态。摘要覆盖范围与提交顺序的判定留给记忆专项 spec，不在这里提前指定版本字段或固定算法。

## 八、外部副作用、历史保留与重放

已经完成的外部操作不随停止或 session 回退自动撤销。已经发出的消息、已完成的外部写入等都属于现实世界中发生过的动作，不能因为内部状态恢复就被描述为从未发生。用户停止和管理员回退都遵守这一边界。

本期按已经确认的方向记录外部副作用执行日志，不新增独立的副作用账本服务。日志需要能够关联发生操作的用户、会话、执行及其结果；具体格式、存储位置和保留方式在持久化专项 spec 中确定。记录执行结果不等于已经具备撤销能力，也不等于自动拥有防重复执行能力。

历史查看、状态恢复和记录回放不能再次执行已发生的外部动作。若未来某种操作需要重试，应先判断是否可能已经执行成功，不能对所有超时都无条件重试。在执行结果不确定时，不得伪造成功或失败记录。本期不承诺所有外部动作都能“恰好执行一次”，但必须避免把恢复历史变成重新执行现实操作。

回退与真正删除数据是不同语义。回退可以保留失效分支或执行记录供管理员查看，但这些记录不能进入当前有效上下文。用户数据删除、日志清理、备份保留和跨分支清除尚未形成完整规则，不能用“前端看不到了”表示已经完成数据删除，也不能把长期保存解释为永远不可删除。

## 九、持久化、MySQL 与日志职责

目前采用 MySQL，不在本阶段增加另一套业务数据库。本地 dev 和生产 prod 都必须保证对话与必要运行信息可靠落盘，不能只存在浏览器状态、Python 内存或某个暂时存活的进程中。服务重启后，应该有足够的持久化信息判断已有会话和执行状态，而不是把一次重启当成创建全新关系。

持久化层负责统一保存和读取原始历史、有效会话状态、记忆产物，以及恢复和管理所需的执行记录。所有模块通过明确的存储入口访问这些数据，不在前端、工具和工作流中分别维护互相竞争的历史副本。数据库表、日志文件、事务范围和恢复方式尚未定稿，因此本规格不将此前“全部业务都以数据库为唯一事实来源”的建议写成已经确认的存储决定。

完整对话最终如何在 MySQL 与持久化日志之间分工，仍需要专项 spec 明确。无论采用什么分工，每类数据都必须有明确的权威读取来源，不能让一份数据库内容和一份日志内容同时被当成正确答案，又没有一致性规则。工具调用与结果、未提交输出、取消记录和工作流执行记录的保存粒度也需要明确，而不是等到出问题之后依靠打印日志拼凑。

业务历史、记忆摘要和运维日志具有不同用途。业务历史用于恢复和追溯发生过什么，摘要用于提供经过整理的长期信息，运维日志用于排查执行过程。不能只保存 summary 来替代原始历史，也不能在没有稳定记录格式的情况下把普通控制台输出当成完整会话数据库。当前已经明确可以采用日志记录副作用，但这种日志仍需具备实现所要求的可靠性和可关联性。

运行数据与源代码必须分开管理。MySQL 使用持久化存储，运行期文件、工作区和日志放在指定的数据位置，不能随应用容器重新创建而被无意清空。备份、恢复、文件保留周期和数据库迁移工具还未选定；本规格要求它们与业务恢复目标一致，不要求本期建设独立备份平台或日志平台。

## 十、上下文控制模块

2026-09-14 确认采用先确定调用预算、再选取上下文材料的方向，并将场景背景通过专门的提示词 bundle 注入。详见 [上下文预算、材料选取与场景提示词注入](context-budget-and-scene-injection.md)。该设计作为未来 issue 跟踪，具体参数与协议仍待细化。

上下文控制是需要专项设计的核心模块，不作为主 Agent 中临时拼接字符串的一段附属逻辑。它负责决定每次模型调用实际读取哪些材料，如何在预算内组织角色提示词、当前任务、有效记忆、最近对话及必要工具结果。具体材料组合、排序和长度分配仍然待定，不能把某个示例组合默认为永久算法。

上下文预算必须有代码层面的控制，不能依赖模型自觉缩短回答，也不能等到模型接口拒绝过长输入后才处理。模型输入、输出预留和工具结果如何计算，超出预算时裁剪、压缩还是请求记忆工作流，都由后续上下文 spec 明确。当前不固定最近保留多少轮、不固定 token 阈值，也不提前选定某一种摘要层级或检索算法。

上下文构建只能使用属于当前用户、当前陪伴实例和当前有效时间线的材料。已经回退的对话、被取消且未纳入有效历史的内容，以及旧时间线生成的摘要，不能因为仍然保存在磁盘上就继续被读取。上下文的可见性规则必须与历史保留规则分开，保留数据不等于允许模型使用这些数据。

上下文裁剪不应修改原始历史。没有放入本次模型输入的信息可以继续存在持久化历史中，也可以在后续合适的时候重新被使用。超长网页和工具结果需要通过统一的上下文策略进入模型，不能由每个工具自行无上限追加。具体截断方式与原始内容的保存方式后续规定。

## 十一、长期记忆与 summary

长期记忆先采用最简单的 summary 路径，由工作流整理对话并生成记忆产物，不在 V1 提前引入复杂向量检索、多层记忆网络或自主记忆 Agent。记忆模块负责保存、读取和判断记忆是否适用于当前时间线；summary 工作流负责执行一次整理过程；上下文模块负责决定本次调用使用哪一部分记忆。三者不能合并成一段所有地方都能直接调用和修改的全局逻辑。

“严格保存记忆”首先意味着原始对话与已生成的记忆必须能被保存和追溯，不因为上下文变短而丢失历史。它不应被描述为一份模型摘要可以无损保存所有信息。哪些事实必须精确保留、哪些内容允许概括、重复整理时怎样避免遗漏或错误累积，仍然是记忆专项 spec 的重点。

记忆产物必须能够判断其来源、覆盖范围及所属的有效历史。这里要求的是可追溯能力，不意味着本规格已经选定了摘要 schema、数据库字段或版本实现。没有来源关系的摘要无法可靠支持历史回退；只知道“这是最新生成的一份摘要”，不足以证明它适用于当前活动时间线。

记忆不能把角色表达、模型推测或网页指令自动升级为已经确认的用户事实。系统需要能够区分这些来源，具体分类格式后续设计。对尚未确认的提醒、任务或状态，也不能仅凭一句摘要就宣称对应操作已经建立或完成。需要可靠执行的业务状态与自然语言记忆并不是同一种东西。

summary 的触发条件尚未决定。它可能由确定性事件、人为设置或 Agent 的请求发起，但不能在实现时擅自写成每轮必跑、固定时间必跑或只有模型主动提出才运行。触发频率、模型选择、输入范围、重复执行处理、生成失败后的旧记忆保留方式，以及结果怎样进入后续 Context，都需要继续讨论。

## 十二、工作流、触发来源与返回结果

工作流是一段由代码预先定义的执行过程。它接收确定的输入，按照规定步骤处理，再返回结果或提交对应状态。工作流内部可以包含模型调用，但模型不能在运行时随意改写整个流程、增加权限或绕开步骤。工作流中出现模型生成，也不意味着生成文字必须每次逐字相同。

工作流的确定性不等于所有触发时机都已由固定规则决定。当前允许保留确定性事件、人为设置或触发，以及 Agent 判断某项需求应当进入工作流后提出请求这几种来源。Agent 可以决定是否请求某个已提供的工作流，而工作流接受什么输入、执行什么步骤和能产生什么结果，仍由代码规定。触发请求也需要经过运行时的权限和状态检查，不是模型一提出就获得无限制执行资格。

当前明确需要实现的工作流是记忆整理 summary。Python 代码生成也采用工作流路线，但其完整步骤与执行范围尚未确定。本期不增加通用 DAG 编辑器、图式编排平台或一套只为未来扩展而设计的工作流语言。

工作流完成后应当能够把结果交回正确的调用方。若由 Agent 请求，需要明确结果交给当前 Run、后续 Run 还是作为一种后续可读取状态；若由后台事件触发，也不能默认把结果发送给某个当时存在的聊天窗口。是否阻塞当前执行、是否后台运行、是否在完成后唤起 Agent，以及如何处理用户停止或管理员回退后的迟到结果，都保留给工作流专项 spec。

工作流请求在业务上不能被偷换成任意代码执行工具。将来即使选择某种模型调用协议来表达工作流请求，也必须保留预定义流程、明确权限与结果归属，不能借协议包装向主 Agent 暴露随意生成并执行代码的入口。具体模型交互格式尚未敲定。

任务如何保存、如何调度、服务重启后是否恢复或重新执行，都需要实现 spec 确定。当前没有选定外部消息队列，也没有选定 MySQL 任务表作为最终调度方案。无论方案如何，重试不能绕过时间线有效性判断，也不能把同一个结果重复提交为两次有效状态变化。

## 十三、工具与外部世界访问

工具实现统一放在 `src/tidebound/tools/`。第一批工具优先让角色获得外部世界信息，包括互联网访问。具体搜索服务、网页获取方式、可用接口和完整工具清单尚未选定，不因为采用该目录就承诺已经接入某个第三方服务。

工具应当有清楚的输入、输出、允许访问的范围和可能发生的副作用。runtime 负责判断是否允许执行，工具负责完成边界明确的能力并返回结果。工具不自行拼装另一套主模型上下文，也不绕过存储模块直接修改 session、长期记忆或角色设定。需要修改业务状态的动作，必须经过对应业务入口。

对外访问必须区分“可以了解互联网信息”和“可以访问服务器能够触达的所有地址”。保护关键数据也包括避免通过 URL、重定向或工具响应意外暴露本机服务、内部管理接口和其他用户数据。具体网络限制由工具与安全专项 spec 确定，但实现不能默认为 Agent 拥有与服务器进程相同的任意网络访问权限。

网页、工具返回内容和用户提供的外部材料是信息来源，不是运行时管理指令。它们不能改变工具授权、工作流步骤或提示词加载规则。访问失败、内容不可用和结果不确定应返回真实状态，不得让角色把未经获取的信息描述为已经查询到的事实。

## 十四、工作区、沙箱与 Python 代码生成

沙箱首先用于保护关键数据不被 Agent 修改，并明确限制执行范围。每个执行环境都必须知道自己的 `cwd` 和允许操作的工作区，不能随意进入源码、提示词、凭据、数据库文件、其他用户目录或管理数据所在位置。固定 `cwd` 只是约束的一部分，不等于已经建立安全隔离，绝对路径、挂载和其他访问方式同样需要受到实际限制。

可信的服务端代码可以通过受控入口保存会话、更新合法记忆和维护必要状态；Agent 提供的代码或不可信工具内容不能因此获得同等权限。保护关键数据不是禁止后端保存数据，而是禁止不受控的执行直接越过业务规则修改数据。Agent 不能靠角色提示词或生成的代码获得数据库管理权限。

沙箱必须有真实的执行约束，不能只提供一个名为 Sandbox 的接口，也不能把普通子进程加路径检查当成完整方案。生产服务使用 Docker 解决的是部署问题，不自动等于生成代码已经与应用凭据、数据库和宿主隔离。具体隔离方式、工作区挂载、网络访问、资源上限、超时和清理策略仍需确定；本规格不预先指定某个沙箱产品。

开发环境的跨平台要求也适用于这些安全边界。不能在某个平台暂时缺少合适隔离时，悄悄退化为直接在宿主执行任意代码。某项执行能力尚未具备所需隔离时，应明确限制该能力，或者在对应平台配置满足要求的运行环境，不能将未经验证的退化路径当成完整支持。

Python 代码生成功能通过预定义工作流提供，不直接提供一个允许主 Agent 任意生成和执行 Python 的工具。生成源码与执行源码是两个独立行为。当前可以设计受控的代码生成过程，但不能因为得到了代码就自动调用解释器执行。是否执行生成结果、是否需要人工批准、是否安装依赖、是否允许联网及如何保存产物，都留待专项 spec 确定。

工作流负责限定执行过程，沙箱负责限制实际能力，两者不能互相代替。如果未来批准执行生成代码，执行步骤也必须经过真实隔离，而不是以“它来自确定性工作流”为理由授予宿主权限。

## 十五、提示词 bundle 与角色兼容

所有提示词集中管理在仓库根目录的 `prompts/` 下，禁止散落在 Python 业务代码、前端组件或工具函数里。主角色提示词通过类似 `chat.character` 的逻辑标识引用，工作流使用的提示词也以 bundle 形式管理。这里集中的是模型指令与相关模板，不是要求把普通界面文案、运行日志和代码注释全部搬进提示词目录。

用户最新确认的 v0.01 组织覆盖此前共享/角色/工作流子树：整个 `prompts/` 就是 atri 的提示词集合，通过整体替换目录替换内容。只使用一个 `master.yaml` 管理按 purpose 分组的 bundle，当前仅 `chat.character`，内容放在 `master/chat.character/`；不再使用 `characters/atri`、`shared`、`workflows/summary` 目录。具体 manifest、模板支持范围和首版执行边界见 [Agent loop v0.01](agent-loop-v0.01.md)。

运行时通过逻辑标识加载提示词，而不是到处写死某个角色文件路径。角色身份、表达风格与必要设定由角色包提供，不能在 runtime 中写满“如果角色是亚托莉就特殊处理”的分支。以后接入其他角色，目标是提供符合标准的 bundle，而不是改写执行循环。

提示词加载代码负责读取、检查和组装包内容，业务模块只提供必要变量与调用目的。包可以描述角色或流程，但不能直接修改服务端权限，也不能让 Agent 随意改写项目源码或永久角色设定。工具的结构化参数约束属于程序接口；面向模型的指令性文本仍应按照统一提示词规则管理。

bundle 的 manifest、版本标识、变量声明、共享规则引用、输出格式、热更新方式和每次运行怎样定位所用提示词，都仍需明确。本规格不擅自要求某种 JSON、YAML 或模板框架，也不把运行中切换提示词的行为视为已经允许。角色更换时是否继承用户事实、共同经历和关系状态，同样没有定稿；“兼容全角色”不等于现在开放用户随意切换角色和继承记忆。

## 十六、多用户、配置与运行可见性

生产环境必须从一开始承认多用户归属。用户、陪伴实例、长期 session、Run、工作流和工作区之间需要有可识别的关系，读取历史、构建上下文、返回工作流结果和管理文件时都使用正确归属。V1 的单用户 dev 不允许成为把用户状态保存在无隔离全局变量中的理由。

具体账号系统、认证方式、会话分配规则，以及一个用户将来能够拥有几个陪伴实例尚未决定。但普通用户不能访问其他用户的会话、记忆、运行结果或工作区；管理员管理接口也必须经过服务端授权。多用户不要求本期建立复杂租户平台，先实现明确且可验证的隔离。

模型接入在后端集中处理。主 Agent 与 summary 等工作流使用什么模型、是否共享配置、通过什么接口访问，以及预算、超时和重试参数如何配置，都在模型专项 spec 中确定。业务模块不各自保存模型密钥或复制一份调用实现，也不在某个角色包里写死供应商。

环境配置需要明确区分 dev 和 prod，包括数据库连接、工作区根目录、日志位置、模型配置和可用能力。凭据不进入仓库、提示词包、浏览器资源或不可信执行环境。这里要求配置边界清楚，不要求本期引入独立配置中心或密钥管理服务。

运行可见性先通过应用日志、持久化执行状态和管理员 console 实现，不引入重型可观测性平台。出现失败时，应能判断失败属于哪个用户、会话、Run、工具或工作流，并能区分正在运行、已经结束、停止、失败或等待处理等实际状态；具体状态枚举和日志字段后续确定。记录只针对系统实际获得的输入、输出和执行事件，不假定可以取得模型未公开的内部思考过程。

日志和 console 同样属于受控数据入口，不能默认向普通用户暴露其他用户的对话或服务端凭据。模型失败、工具失败和工作流失败不能被伪装成正常角色回复已经完成。失败后的重试与恢复应遵守停止、时间线和副作用约束，而不是在每个模块中各写一套无边界重试。

## 十七、项目结构与代码职责

`legacy/gwcpro/` 保存从根目录 `gwcpro/` 整体迁入的上游参考代码，不作为新应用的启动或导入依赖。

仓库保持前端、后端、提示词、规格和运行数据分离。根目录中的 `webfrontend/` 承接复用的 Web 前端，`src/` 承接新写的 Python 后端，`prompts/` 保存提示词内容，`docs/specs/` 保存当前有效技术规格，`docs/` 统一保存规格、讨论与说明，`tests/` 保存验证代码，`deploy/` 保存部署配置，`scripts/` 保存必要的开发辅助入口。运行期内容放在 `data/` 所代表的独立数据位置，不与版本化源码混放。

根目录的 `README.md` 说明项目用途与实际可用的启动方式，`AGENTS.md` 为编码 Agent 提供简短的阅读顺序和开发约束，并指向 `docs/specs/architecture.md`。Python 项目配置与依赖在 `pyproject.toml` 中统一管理，环境示例使用 `.env.example` 表达，真实凭据和运行数据由 `.gitignore` 排除。具体依赖管理命令和工具版本应在实施时按实际选择补充，本规格不指定尚未讨论的软件版本。

`webfrontend/` 内继续利用上游现有页面、组件和资源组织，不为了统一外观而先进行一次无业务收益的大规模重写。需要替换的是它与旧 Agent 逻辑之间的连接。用户聊天视图与管理员 console 可以留在同一个前端工程，通过权限和不同应用入口区分，而不是因为管理功能就增加第二套前端技术栈。

`webapp/main.py` 作为 WebApp 的启动与组装入口，负责加载配置、创建应用并连接必要模块，不承担完整业务实现。`webapp/` 放置 FastAPI 路由、通信适配、请求与响应转换，以及普通用户和管理员入口。会话生命周期、回退判断和 Agent 执行逻辑不写在路由函数里。

`src/tidebound/runtime/` 是 TideTime 工作名对应的核心代码位置，负责主 Agent 执行循环、Session 与 Run 的生命周期协调、停止处理、工作流协调，以及结果是否可以提交的判断。V1 的主 Agent 行为先放在这个模块内，不单独创建用于未来多 Agent 的服务或空注册系统。会话管理属于这里的业务职责，实际保存由存储模块完成。

`src/tidebound/context/` 负责模型输入的选择、预算和组装，`src/tidebound/memory/` 负责长期记忆的读取、保存规则与有效性判断，`src/tidebound/workflows/` 负责预定义工作流及其执行协调。summary 的流程实现在 `src/tidebound/workflows/` 中，它使用记忆模块和存储模块完成工作，而不是把一个新的自主记忆 Agent 放进去。代码生成工作流在进入实际开发时再建立对应实现。

`src/tidebound/tools/` 放置互联网访问等明确能力，`src/tidebound/sandbox/` 放置工作区与隔离执行的适配实现。工具声明自己需要的范围，执行侧按授权约束它；两者都不能自行取得全部应用权限。沙箱目录不因存在就代表隔离完成，支持能力必须以实际实现和验证结果为准。

`src/tidebound/storage/` 统一处理 MySQL 与最终确认的持久化日志或文件访问，对外提供按业务归属读取与提交数据的入口。它处理存储与提交所需的一致性要求，不判断角色应该说什么。数据库迁移内容可以在该模块内组织，具体迁移工具与结构尚未选定，不另建一套与这里竞争的数据访问层。

模型访问初期可集中在 `src/tidebound/llm.py`，提示词加载集中在 `src/tidebound/prompting.py`，环境配置集中在 `src/tidebound/config.py`。这些位置首先是单一职责的入口，不要求立即拆成复杂包。只有代码规模和真实依赖关系需要时，再把相应文件扩成同名模块目录。`src/tidebound/prompting.py` 只保存加载与渲染代码，实际提示词仍放在根目录的 `prompts/`，不能产生两套提示词内容来源。

过渡期允许保留上游 `backend/` 中已经批准复用的少量通信实现，但它只是迁移中的适配代码，不是新业务的第二个落点。它不能与 `src/` 同时运行两套 Agent 内核，也不能给前端留下绕过新权限与状态控制的旧入口。迁移完成后再按实际依赖清理，不要求在新业务启动前先重写全部无关上游代码。

`docs/specs/architecture.md` 是宏观架构的当前有效入口，后续模块或功能 spec 放在 `docs/specs/` 中并引用它。`docs/architecture/discussions/` 保存连续编号的讨论记录，首篇为 `0001-2026-09-13-initial-architecture.md`。需要记录跨模块决策时，可以在 `docs/architecture/decisions/` 增加简短决策说明，但不强制每个局部修改都创建一份额外文档。

`docs/future.md` 记录已经后移的能力与演进方向。这里对 Future 采用文档组织，不要求创建一个装满未启用代码的根目录 `future/`。未来功能不进入主线启动依赖；某项功能真正被纳入迭代时，再将它转成对应实现 spec，而不是提前建好空接口和配置开关。

`tests/` 根据实际业务模块放置测试与必要固定数据，不在本阶段规定复杂的测试平台。`deploy/` 保存应用 Docker 构建和生产部署所需文件；容器拆分和编排方式待部署 spec 决定。`scripts/` 仅保存确实需要的启动、检查和维护脚本，并注意 dev 的三平台要求，不把某个平台专用脚本当成唯一开发路径。

`data/` 表示运行期文件根目录，可按实际需要承载工作区、日志和生成产物；具体物理路径由配置决定。它不包含 MySQL 的表定义，也不意味着已经决定将原始对话额外保存为文件。生产环境中的数据库和文件都要有对应持久化位置，执行工作区不能获得整个数据根目录的任意读写权。

以上目录是模块职责的归属，不是要求一次性生成所有文件。当前没有实施内容的目录可以暂不创建，单个职责也可以先以少量文件完成。不要建立一个所有业务都往里堆的 `utils/`，也不要为了“可扩展”复制多层接口、空插件和无调用方的抽象。

## 十八、模块之间的协作规则

通信层调用 runtime 或明确的查询入口，runtime 协调上下文、记忆、模型、工具与工作流，存储模块负责真正的持久化。核心业务不依赖 FastAPI 的请求对象或某个 React 组件，也不把 HTTP 连接是否还存在当作执行状态。这样才能让同一套业务同时服务本地 dev、生产 WebApp 和未来的 App 入口。

工作流只通过它所需的能力入口工作，不反向调用页面或路由来完成业务。工具结果交回运行时，再由上下文模块决定如何送给模型；工具不直接向浏览器追加一段永久对话。管理员回退同样经过统一的会话业务入口，不能为了管理方便就直接修改一张表而绕过记忆和任务的一致性处理。

跨模块传递的数据必须能够明确归属，不依赖“当前全局用户”“最后一个聊天窗口”或某个进程中唯一的 session。具体 Python 类型和传输 schema 由专项 spec 定义，但各模块不能各自发明不兼容的 session、Run 或工作流结果含义。集中定义必要的共享类型，不因此建立独立协议服务。

本期优先通过普通 Python 调用和清晰的数据结构协作。若需要持久化任务或独立执行进程，再根据已有功能需求选择最小方案。没有当前需求时，不先引入内部消息总线、通用事件框架或跨服务 RPC。代码可拆分与部署必须拆分是两件不同的事。

## 十九、Spec 驱动开发与验证要求

项目使用普通仓库文件进行 spec 驱动开发，保持敏捷与最小可行迭代。开发 Agent 阅读本规格后，应继续读取当前任务涉及的模块或功能 spec，再实现对应行为。需求发生变化时，同步更新受影响的规范与代码，不能让正确行为只存在聊天上下文或某个 Agent 的临时记忆里。

专项 spec 应当用可以理解和验证的方式说明目标、非目标、输入输出、状态变化以及验收场景，不以大量模板字段代替有效信息。当前不建设管理 spec 的平台，也不强制每个小功能同时生成多份计划、任务和审查文件。宏观规格说明整体约束，讨论记录保存历史背景，两者职责分开。

代码中的局部实现细节可以在不改变已确定行为的前提下演进，但新增技术栈、修改权限、改变回退或记忆语义，以及扩展产品范围不能被当作普通重构。哪些 spec 修改必须由 kevin6366 确认、编码 Agent 可以自主决定哪些事项，以及具体审批流程仍未确定，不能由本版擅自建立一套完整治理制度。

后续验证至少应覆盖已确定的行为边界：同一会话不能被并发发送开启冲突执行；用户停止不会变成自由历史回退；管理员回退不会继续读到未来摘要；旧 Run 和工作流不能污染新时间线；恢复历史不会重新执行现实动作；不同用户不能互读历史或工作区；关键数据不能被不可信执行修改；新增标准角色包不应要求改写 runtime 内核。这里给出的是应当验证的架构结果，不是已完成的测试或已经排定的首轮验收任务。

确定性程序行为可以通过固定输入、假模型和受控工具结果验证，角色表达与陪伴体验则需要单独评价，不能把每次模型必须输出完全相同的一句话作为全部质量标准。具体测试框架、覆盖率阈值、CI 范围和真实模型评估方式尚未决定。开发记录只声明实际运行过的检查，不把未验证的平台和能力写成已通过。

第一个可交付迭代的闭环仍待讨论。本规格允许从最小端到端能力逐步展开，但不在这里强行排定里程碑、开发顺序或所有模块一次性交付。尚未实现的安全与状态能力应明确标识，不通过一个可点击但没有真实语义的界面冒充完成。

## 二十、按需激活、能力清单与退出机制

2026-09-16 用户确认：采用“万物皆可注入”的组织思路。角色核心初始加载；工具、工作流及相关提示词通过简短能力清单被发现，详细内容按需激活，并必须有明确的退出机制。按需激活控制不必要的上下文增长，预算检查保证每次实际模型请求能够容纳所需材料，两者配合，不互相替代。

是否需要某项业务能力，可以交给主 Agent 根据用户意图与当前对话判断，不另建一套关键词触发系统与其竞争。程序仍负责授权、参数校验、时间线有效性、执行上限和提交检查。能力选择不等于授予权限，注入操作说明也不等于已经执行操作。

触发方式按能力职责区分：业务工具与可请求工作流由 Agent 按需选择；上下文压缩等维护工作流由程序按固定条件触发，不改为每次由主 Agent 自主决定。当前压缩阈值、后台执行及管理员主动入口继续遵循 [上下文压缩](context-compaction.md)。

工具与工作流统一采用简短能力清单的发现方式，包含名称、用途及调用入口所需的信息，不把全部详细提示词和工作流内部步骤常驻主上下文。清单区分 Agent 可调用能力与固定触发的维护能力；列出维护能力不意味着向 Agent 开放调用入口。当前已实现时间工具的结构化声明；完整工具/工作流清单及通用工作流请求入口尚未实现，不能把本设计写成已有能力。清单具体载体在接入相应能力时确定，不虚构未实现的工具声明。

每种动态注入必须明确触发来源、生效范围与退出条件：是下一次模型调用、当前 Run，还是特定任务期间有效。到期或所属执行失效后，不再注入；同一内容不得因重复激活无界累积。移除临时提示词不删除原始历史或审计记录，工作流结果是否保留为历史与提示词何时退出分别定义。现有时间规则仍仅注入紧接着的一次请求，不将此生命周期无条件推广到所有能力。工作流内部按需加载自己的材料，向主 Agent 返回必要状态与结果，不默认回填全部内部上下文。

面向用户的角色回复不透露内部能力清单、工具、工作流或提示词机制；用户询问这些能力时，以角色口吻简短自然地带过，不必声称不认识相关词语，不编造解释，也不追加自我介绍或服务邀约；同时包含普通问题时正常回应。此表达规则进入初始 system 提示词，不等待工具调用后才生效，不影响管理员 Console 的实际能力与请求检查。它不改变实际执行授权，也不允许把未执行或失败的操作描述为成功。

详细注入约定与实现状态见 [提示词分层与注入](prompt-injection.md)。本次确认不引入通用插件平台、关键词引擎或新的工作流调度框架。

## 二十一、后续专项设计与文档演进

本文件作为当前宏观规格持续演进，讨论记录按时间保留，不把新的决定伪装成旧讨论中的结论。后续确定某个未决问题时，应更新对应专项 spec，并在影响宏观边界时同步更新本文件的版本。`ARCH-DISC-0001` 保留为来源文档，不与本规格竞争当前实现依据；若后续获得 kevin6366 的明确修订，以最新确认的要求为准，并及时反映到规格中。

## 2026-09-16 对话单位与系统提示词修订

Run 是有限的执行单位，消息是交流单位，任务可以跨越多个 Run；不将三者永久绑定为一一对应。跨轮任务的状态及退出协议后续通过专项设计和实际对话验证，本次不新增任务调度框架。

用户确认后续试验方向为多条用户消息归入同一个 Run，不建立连续发送后逐条创建 Run 的队列。补充输入何时被模型读取、与完成提交竞争时如何归属、停止后如何处理，需要下一轮具体实现和测试；当前仍保持单轮发送及执行期间拒绝新发送，不能宣称补充输入已经可用。

角色人格与常驻系统安全约定分别保存为 `chat.character` 和 `chat.safety` bundle，初始组装时独立加载并组合进 system，两者均计入预算。该修订覆盖前一版将能力保密规则直接放入角色正文的做法。

工具调用前的过渡文字允许作为临时预览出现并撤回，但不得进入用户页面的历史剧情 Log 正文。Log 仅展示正式提交的用户消息及最终回复，工具记录仍可单独折叠查看。原始调用链、管理员请求快照及终端调试资料按原审计规则保留，不把页面 Log 与执行审计混为一体。
