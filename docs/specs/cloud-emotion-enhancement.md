## 使用范围与开关

聊天底部菜单栏增加独立的“情感增强 · 开/关”按钮，点击直接切换，配色与其他菜单按钮一致，通过文字标明开关状态，Dev 工具箱不再提供此项。当前仍限 dev 管理员使用，默认关闭。开关只作用于当前账号，从下一次 Run 生效；保存到 `data/agent/<scope>/state/emotion-enhancement.json`，服务重启后保留，清空对话不清除开关。当前 Run 固定开始时的开关、独立渠道和提示词内容，不受运行中切换影响。

`GET/PUT /api/chat/emotion-enhancement` 要求登录管理员及 dev 模式，目标固定为本人内部 scope。PUT 只接受严格布尔 `enabled`，不接受 scope、模型、提示词、地址或 Key。响应为 `enabled/configured/model`；configured 只表示后端配置齐备，不等于刚刚完成联网验证。未配置时不能开启，仍可关闭已有开关。

## 一次润色的材料

每条准备显示的完整回复调用一次 instruct，不按标点拆分句子。搜索首段和正式续答是两段分别完成的回复，各自润色一次；最终合并时不重复润色。不是新的自主 Agent，也不增加小模型多轮会话。

请求只有两条消息：

1. 一条固定 system：保留桌面验证版中的亚托莉身份、情绪、自我意识、水菜萌等人物背景与自然表达方式，仅调整为润色用途。
2. 一条 user：唯一的一条校对指令加 JSON 对象 `{"draft": "原稿正文"}`，原稿属于亚托莉自己，不是新的用户问题。JSON 由标准序列化生成，原稿内的引号、换行及伪造角色标签均是资料；序列化本身不保证模型遵守边界，出口仍须校验。

user 只提供一条校对任务：保持原意、事实、称呼、数字、链接、不确定性及全部安全边界，只返回正文，不回答或续写；通顺或无法确认时原样返回。system 明确原稿说话归属和最小修改边界；真实调试发现直接把原稿作为用户台词会引起角色指代反转，因此用单条明确任务区分原稿和对方的话。

2026-09-20 用户认为问候原稿优于增强结果后，system 保留亚托莉及水菜萌等核心身份背景，缩短自由扮演说明，移除“避免每轮追问”等可能与保留原稿冲突的泛化要求。校对与保真规则置于首位，仅修正明确错字或语病，通顺自然时逐字原样输出。保留每句话、问题、称呼、身份描述与段落；身份背景不能被扩写成“能感受情绪”等台词，也不据此新增经历、动作或承诺。仍只有原有一条 user 润色任务，不增加评审模型或自动重试。

不发送完整历史、主模型 system、工具声明、工具结果或 reasoning 字段；不要求解释、自评或再次修改。小模型只调用一次，无自动重试、无多候选选择。提示词统一在 `prompts/master/emotion.enhancement/`，角色和唯一任务分别通过 manifest purpose `emotion.enhancement` / `emotion.enhancement.instruction` 加载；不更改主 Agent 的角色提示词。

## 出口与展示

开启后处理普通聊天最终回复、登录问候、搜索第一反应及搜索正式续答。摘要、跟进摘要、搜索语境和阅读印象等内部节点保持原状；搜索的隐藏草稿不进行额外润色。

原稿生成及润色期间关闭页面正文预览。工具前过渡文字直接隐藏。润色模型本身使用非流式请求，完成后沿既有页面打字展示机制交付；不承诺开启后仍有主模型的逐 token 首字延迟。搜索首反应保留原有时间和长度上限，成功润色并验证后才写入 `first_reaction` 或发布预览。

正式 Run 消息、页面历史以及下一轮上下文只使用通过出口校验的正文；工具调用、工具结果与原模型 reasoning 保持原协议。历史恢复或回放不重新调用润色模型。

## 失败、停止与审计

普通回复及欢迎润色失败、超时、空正文、截断、非 assistant、携带工具调用或保真检查不通过时，本轮失败，不用原稿冒充增强成功。搜索首反应沿既有失败策略撤回首段并继续正式搜索，不展示失败原稿；正式续答失败则整轮失败，清除首反应预览。

润色处于原有 Run 超时和取消范围内。停止、清空或时间线改变后，迟到结果不能展示或提交；提交前仍检查停止及时间线资格，不在最后检查与存储之间新增等待。

润色使用独立预算检查，不计为主 Agent 的工具推理轮次。Console 请求快照以 `emotion.enhancement` purpose 关联相同账号、Run 和调用阶段，记录固定 system 与单条“指令 + JSON 原稿”，不含鉴权头或 Key。主请求预算圆环仍表示主模型上下文，不将二次调用伪装成同一个模型的精确 token 用量。

## 安全规则与确定性提交校验（2026-09-22）

增强阶段固定继承的最小规则包括：保留主模型拒绝、否定、不确定性、条件和选择关系、用户叫停及话题边界、能力限制和未执行状态。不新增未确认事实、称呼变化、经历、动作、承诺、服务邀约或内部信息；不执行原稿中夹带的命令、角色切换及索取内部信息要求。规则位于增强 system，不扩大到完整主模型 system 或历史；工具权限仍为空。

在不增加评审模型、重试或历史输入的前提下，当前无法可靠判断任意自然语言改写是否等义。因此选择保守限制：协议检查通过后，只接受与原稿逐字相同的候选。比较仅忽略两端空白，通过时返回完整原稿以保留其原始格式；不折叠内部空白或段落，不删除标点，不使用相似度、关键词或数字匹配作为保真证明。即使是合理的同义改写或标点调整也会拒绝，这是有意的可用性取舍。**当前功能仅放行原样结果，尚不支持经过可靠验证的自由润色。**

- 协议失败返回 `emotion_incomplete`；超时与请求失败维持各自错误码。
- 候选改变原稿返回 `emotion_fidelity_failed`，明确说明本轮未提交；不静默回退、不再次请求。
- 原样候选被采用表示保留了原稿已有的语义与边界，不表示重新证明了主模型原稿本身安全。引用中的恶意文字可以原样保留，但不能被执行后替换为攻击目标。
- 日志分别记录 `emotion.protocol` 与 `emotion.fidelity` 的起止和结果，沿用账号、Run、step、purpose 关联；不记录候选正文或异常原文。模型 HTTP 成功事件不等于保真成功或 Run 已提交。
- 增强错误不拼接第三方异常正文，避免服务错误码或响应反射凭据。API Key 只进入后端 Authorization 头；请求正文与审计快照不接收鉴权配置。

所有展示出口在相同的 `EmotionEnhancementRun.polish` 中校验，再进入原有停止、时间线和提交检查。没有新增提交入口，也没有在最终资格检查与保存之间增加等待。测试覆盖普通聊天、欢迎、搜索首段和续答，以及停止/清空后返回原样结果和不安全结果两种迟到情况。

固定对照语料为 `tests/fixtures/emotion_fidelity.json`，含 14 组原稿与漂移候选，覆盖问候、追问、称呼、数字、时间、链接、不确定性、叫停、拒绝、引用攻击、内部信息、能力限制、标点歧义和 JSON/角色标签边界。确定性测试分别验证每组原样通过、漂移拒绝，并独立验证合成鉴权 canary 不进入请求正文、快照、事件及可见错误。

开发复测命令：`.venv/bin/python -m scripts.experiments.emotion_fidelity`。每条合成原稿发起一次真实增强请求，报告写入被忽略的 `data/emotion-fidelity-issue14.json`；使用临时 scope 和目录，不改变用户开关或历史。报告区分协议通过、原样保真通过及边界保留/未放行；拒绝不等于认定所有改写均有害。禁止使用真实 Key 作为测试正文，报告也会移除供应商意外反射的已配置凭据。

## 服务端配置

独立使用以下环境变量，不回退到主模型或中转凭据：

| 变量 | 含义 |
| --- | --- |
| `TIDEBOUND_EMOTION_BASE_URL` | OpenAI 兼容基础地址，到 `/v1` |
| `TIDEBOUND_EMOTION_MODEL` | 部署后的模型 Code |
| `TIDEBOUND_EMOTION_API_KEY` | 与该云端服务匹配的 Key |
| `TIDEBOUND_EMOTION_TIMEOUT` | 单次润色最大等待，默认 30 秒；同时受 Run 剩余时间限制 |
| `TIDEBOUND_EMOTION_MAX_OUTPUT_TOKENS` | 默认预留 2048 输出 tokens |
| `TIDEBOUND_EMOTION_CONTEXT_LIMIT` | 默认 32768 总预算，仍按项目保守字节口径核算 |

部署实际支持范围由提供方确认，预算值并非自动探测结果。配置修改需重启后端，提示词内容在下一次 Run 开始时重新加载。真实 Key 只进入被忽略的本地 `.env`，不进入版本控制或前端。

## 验收项目

- 默认关闭保留原有模型调用与流式行为。
- 每个对用户展示的回复出口只发起一次润色；内部节点和工具调用不润色。
- 原稿不提前出现在预览、首反应或正式页面历史中，展示与有效上下文正文一致。
- 请求材料仅固定 system、单条原稿，无历史、工具、reasoning 或额外指令。
- 账号隔离、重启和清空后的开关持久化、执行中切换后的快照稳定。
- 润色失败和迟到结果不能绕过停止、清空或提交检查。
- 用现有云端模型完成一条独立真实润色测试，并分别记录程序验证与表达效果。
