# 提示词分层与注入

文档编号：`PROMPT-SPEC-0001`；版本：`0.1`；日期：`2026-09-14`。

本文依据用户确认的时间工具规则拆分要求，定义提示词注入的统一职责边界与当前实现。它补充 [宏观架构](architecture.md) 和 [Agent loop v0.01](agent-loop-v0.01.md)；复杂材料选取、场景及记忆仍见 [上下文预算与场景注入](context-budget-and-scene-injection.md)。

## 一、分层原则

所有面向模型的提示词正文统一保存在 `prompts/`，按用途分开管理，由后端在模型请求前组装。角色文件不引用或复制工具使用规则。新增注入内容必须明确来源、启用条件、位置、生命周期及预算处理，不能只新增文件而不接入调用链。

| 材料 | 职责与来源 | 当前状态 |
| --- | --- | --- |
| `chat.character` | 稳定身份、人格和表达方式 | 已实现 |
| `tools.injection.<group>` | 一组工具的使用时机、结果解读与行为约束 | 已实现时间工具组 |
| 工具声明 `tools` | 名称、功能描述、参数 schema，由注册表生成 | 已实现，与正文注入分别传递 |
| 工具结果 | 本次执行得到的事实，通过 `role=tool` 回填 | 已实现，不作为系统指令加载 |
| 历史、摘要和记忆 | 当前用户与有效时间线的事实材料 | 已实现完整历史和滚动上下文摘要；独立长期记忆仍待设计 |
| 场景与其他动态注入 | 独立用途的背景或当轮材料 | 尚未实现，具体协议由对应专项规格确定 |

工具提示词不能授予权限。可用能力以服务端注册表为准，执行仍需检查名称、参数和停止状态。工具结果、用户输入和外部文本不能被当作可信提示词文件加载。

## 二、目录与 manifest

当前目录：

```text
prompts/
├── master.yaml
└── master/
    ├── chat.character/
    │   └── chat.character-zh.md
    └── tools.injection/
        └── tools.injection.timetools.md
```

`tools.injection` 是工具提示词目录，`tools.injection.timetools` 是时间工具组的逻辑 purpose，文件沿用仓库 Markdown 扩展名。manifest 为每个 purpose 声明中文默认 variant、唯一 bundle name 和有序 segments；时间工具组引用 `@master/tools.injection/tools.injection.timetools.md`。代码只引用 purpose，不硬编码正文或具体内容文件路径。

目前每个 purpose 仅支持一个中文默认包。正文为静态 Markdown，可去除 Go 风格版本注释，其余动态模板仍拒绝。工具注入不写入 `chat.character` 的 segments，避免角色单独加载时携带能力规则。

## 三、工具调用后的一次性注入

1. 工具注册项用可选的 `injection` 指向逻辑 purpose；`get_current_time` 对应 `tools.injection.timetools`。注册字段本身不发给模型。
2. 首次模型请求只包含角色、有效历史、本轮输入及结构化 `tools` 声明，不包含工具注入规则。模型依据工具名称、描述和参数判断是否调用，不扫描用户关键词来提前注入。
3. 模型返回工具调用后，后端按注册表校验并处理，追加 assistant 调用与 tool 结果。然后收集本批已调用工具的注入标识，按调用顺序去重并加载正文。
4. 紧接着的那一次模型请求，将临时规则用空行接在角色内容后，作为本次 `system` 内容。历史和本轮工具消息照常传递，工具声明仍放在 `tools` 字段。
5. 临时规则使用一次即消耗，不修改固定角色内容、不追加到消息历史、不保存进已提交对话，也不自动延续到本轮更后面的请求或下一 Run。如果模型再次调用同一工具，那次新调用会重新触发一次注入。
6. 同批多个调用共享 purpose 时只注入一份；不同 purpose 按调用顺序拼接。未注册工具无注入。已注册工具返回参数错误或执行错误时，仍注入一次，便于模型遵守失败后的表达约束；这不表示执行成功。
7. 临时规则在调用处理后读取，缺失或非法时整轮失败，不静默忽略。角色仍在 Run 开始时读取并固定；工具规则在每批调用后形成一次快照，文件修改可以影响之后的工具调用，已经构造的请求不会变化。
8. 每次请求使用实际的“角色 + 本次临时规则”核算预算。注入与本轮消息、工具声明一起属于该次请求的必需材料，装不下时明确失败，不在预算检查后追加。

这是一种工具调用后的提示词注入机制。未来其他注入类型必须各自明确触发条件、放置位置、持续次数和是否持久化，不能把所有注入默认为每轮常驻。

manifest 校验覆盖 purpose 范围、语言、变体和名称唯一性；正文读取与路径、模板校验针对本次选中的包。未调用工具的正文不加载。

2026-09-16 新增 `context.compaction` 和 `context.injection.summary`，分别用于独立摘要调用和历史摘要使用规则。目录、静默后台触发、生命周期与预算见 [上下文压缩](context-compaction.md)。摘要正文属于账号运行数据，不进入角色文件或共享 manifest。

## 四、时间问题的实际链路

```text
请求 1：角色 + 有效历史 + 用户问题；tools 声明时间工具
  → 模型自主提出 get_current_time({})
  → 后端处理调用，回填真实时间或错误
  → 加载 tools.injection.timetools
请求 2：角色 + 本次临时时间规则；消息包含调用及结果
  → 模型生成最终回复，或继续调用工具
请求 3（若存在）：不自动保留请求 2 的临时规则
  → 只注入请求 2 新产生的工具调用对应的规则
下一 Run：不继承任何上轮临时规则，历史仍可包含工具调用与结果
```

时间规则正文以 `tools.injection.timetools.md` 为唯一来源，保留用户指定的先查询再回答、不以旧结果冒充此刻时间、成功后才能确认及不宣称未执行能力的约束。它在工具调用后生效，用于约束后续回答，不承担首次工具选择的引导。真实时间来自 tool 消息，不写入静态提示词。

当前 `tool_choice=auto`，首次是否调用仍由模型根据工具声明和对话决定；没有新增“时间回答必须有工具调用”的确定性检查，也不保证模型必然查时间。

## 五、新增注入的约定与实现边界

新增工具组时，添加独立 Markdown、manifest purpose，以及工具注册项的 `injection` 引用；使用调用后一次性加载与预算流程，不在主循环中加入具体工具提示词分支。无额外行为规则的工具可以省略该字段。

未来场景、记忆、输出协议或当轮引导也应按职责独立管理；在对应专项规格明确前，不预建空文件、动态模板引擎、关键词触发器或通用插件平台，也不将这些材料默认塞入 system。材料位置与保留优先级分开设计，事实与指令分开处理。

本地 Run 记录保存角色包名称和消息链；完整请求另存管理员审计快照，可查看实际组装后的一次性规则，见 [账号与日志 Console](accounts-and-console.md)。审计快照不属于有效历史，不会导致规则持久注入，也不提供执行重放。

## 六、验证要求

- 首次请求和角色单独加载不含规则；工具调用后的紧邻请求包含且仅包含一份规则。
- 同一 Run 再后续的请求不继承规则；重复调用可重新触发；下一 Run 不从历史恢复规则。
- 同批共享 purpose 去重，顺序稳定；未调用的工具正文不加载。
- 缺失注入、非法模板、越界路径与重名包明确失败。
- 临时规则计入对应请求预算，超限时不调用模型。
- 工具消息保持 ID 关联，成功提交、停止与历史隔离语义继续成立。
