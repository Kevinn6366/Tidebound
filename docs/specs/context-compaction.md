# 静默后台上下文压缩

2026-09-22：新增独立的[长期滚动摘要](rolling-summary.md)，后台静默维护，主模型按需读取，跟进工作流共用背景。与上下文压缩使用不同提示词和存储，具体边界以专项规格为准。

2026-09-19 修订：已接入[陪伴工具与跟进工作流](companion-tools.md)。主动清空同时删除可回忆历史正文、摘要与派生状态，仅保留无正文执行墓碑及独立管理员审计；覆盖下文旧版“清空保留旧 Run 正文”的描述。压缩仍保留原文。联网权限由本轮开关控制。

日期：2026-09-16。状态：已接入单 worker dev；本规格覆盖旧规格中“只裁剪、不生成摘要”的行为。依据用户确认，参考 SillyTavern 的“上一份摘要 + 新增历史 → 新摘要”方式，角色提示词不参与压缩。

## 触发与用户体验

每次主模型请求前，以及一轮完整回复成功落盘后，检查：

```text
占用率 =（输入估算 + 主回复预留 + 格式余量）/ 配置上下文上限
占用率 >= 90% → 调度静默后台压缩
```

输入估算包含角色、本次工具规则、工具声明、有效摘要、尚未覆盖的历史和当前轮次，检查发生在任何历史裁剪之前。沿用当前 JSON UTF-8 字节估算，并非供应商精确 token；配置上限仍需要与实际模型匹配，本次没有新增模型能力查询或 tokenizer。

回复落盘后用户可以阅读和输入，后台任务不占用会话的主执行状态，不显示“正在压缩”、不输出聊天消息、不推送摘要正文。90% 至硬输入上限之间，主请求可继续使用原上下文，同时后台生成摘要。下一次模型调用读取已经完成的最新有效摘要。

只有候选请求已经超过硬输入上限，才等待后台任务；停止主执行会中断等待。若上一轮规划的摘要仍不足以容纳当前输入，允许按新材料再规划一次；仍失败则返回明确预算错误，不静默裁掉旧历史或发送已知超限请求。

用户进一步确认：硬超限等待期间保留原请求，执行仍为 `running`，临时阶段为 `compacting`，页面显示“正在整理上下文…”。工作流完成后恢复 `generating` 并自动继续原消息，无需重新发送。SSE 和会话查询均提供这一阶段；停止按钮继续有效。阶段不作为对话正文或永久历史保存。90% 触发但尚能正常请求时仍然静默。

后台每账号最多一个任务。它只读取已提交历史，因此用户停止新的主执行不会取消对旧历史的维护；清空上下文会切换时间线并取消该账号的后台任务，服务关闭会取消全部任务。取消后供应商仍返回的摘要不能发布。

## 顺序节点

文件位于 `src/tidebound/workflows/compaction/`，按用户要求采用真实文件名 `N01-功能.py`，功能部分使用英语。`__init__.py` 通过显式 `import_module` 加载这些带连字符的模块，普通异步函数顺序执行，不引入通用图引擎。

| 节点文件 | 输入与通过条件 | 下一步 |
| --- | --- | --- |
| `N01-ReadValidHistory.py` | 检查所有来源均为同时间线已完成 Run，读取匹配有效前缀的旧摘要 | N02 |
| `N02-PlanCompaction.py` | 自动触发未达到 90% 则正常结束；主动触发跳过阈值；规划完整历史前缀和独立摘要预算 | N03 |
| `N03-GenerateRollingSummary.py` | 旧摘要 + 新增历史生成新摘要；长历史按完整轮次分批，每批通过长度和结束状态检查 | N04 |
| `N04-ValidateSummary.py` | 非空、未超摘要长度、组装后满足本次规划目标且占用严格下降 | N05 |
| `N05-CommitSummary.py` | 再查取消、当前时间线、来源前缀和覆盖进度后原子保存 | 完成 |

异常不跳转后续节点。后台记录失败原因，保留原摘要及原始历史；主请求仍能放入预算时继续正常使用旧上下文。程序校验结构、预算与来源，不宣称能证明摘要语义无损。

## 压缩范围与预算

- 摘要最多占可用输入预算的 15%，作为用户指定 10%～15% 范围内的试验初值；按 UTF-8 字节验证，中文不能直接把字数当作 token。
- 压缩后总占用优先以不超过 70% 为目标，包含主回复预留和格式余量。2026-09-16 修正：若固定内容和摘要额度使 70% 不可达，则按 98% 的总占用上限缩减摘要长度，至少保留 256 字节摘要空间，并校验实际输入严格小于压缩前。降级会写入摘要元数据和调试日志，不改变角色或输出预留。
- 始终保留最近 5 个完整轮次原文；仅摘要覆盖更早的完整轮次。五轮原文使 70% 不可达时采用现有 98% 回退目标；仍无摘要空间则明确失败，不减少保留轮数。保留当前未提交 Run 的原文、工具调用和结果。
- 角色和临时工具规则只参与主请求预算规划，不发送给摘要模型；摘要请求也不提供工具。
- 摘要只覆盖旧摘要之后的新历史，保留的近期原文与摘要覆盖范围不重叠。
- 分批请求输入均校验自己的预算，单个完整轮次仍放不下时明确失败。本期不把单轮拆成不完整协议片段。
- 每次工作流最多 16 次模型调用，每批无效输出最多尝试 2 次，所有批次成功后才发布最终版本。任务使用独立超时，默认复用现有模型和运行超时配置。
- 固定内容过大到连 98% 上限内的最小摘要都放不下时，明确要求调整预算。调小预算不会自动改写已有摘要；原摘要加当前必需内容仍超限时可能需要调大预算。

## 提示词及模型输入

`prompts/master.yaml` 注册：

```text
context.compaction
  → master/context.compaction/context.compaction-zh.md
context.injection.summary
  → master/context.injection/context.injection.summary-zh.md
```

前者只用于摘要调用；后者在存在有效摘要时成为系统使用规则。摘要正文保存在运行数据中，不写回共享 prompts。未引入模板引擎，工作流将 previous_summary、turns、summary_max_bytes 作为结构化资料传给模型。

主模型看到：

```text
system：角色 + 本次临时工具规则（如有）+ 摘要使用规则（如有）
user：明确标记 context_summary 的 JSON 历史资料（如有）
未覆盖的最近完整对话
当前用户输入及当前工具链
```

摘要是历史资料，不作为 system 指令或新的用户授权。摘要规则要求保留事实来源、更正、用户边界、共同经历、重要约定和未完成事项，区分虚构、推测与现实事实。摘要生成不读取 `reasoning_content`。

## 存储、恢复与可检查性

`storage/summaries.py` 把版本写入 `data/agent/<owner>/summaries/<timeline>/<summary_id>.json`，初始时间线目录名为 `initial`。与 Run 文件分目录，避免现有历史扫描把摘要误读为对话。

每版记录覆盖的 Run ID 前缀、父摘要、时间线、提示词名称和内容哈希、模型名、压缩前后输入估算与摘要长度上限。加载时仅采用完整匹配当前已提交历史前缀的版本，按覆盖范围和生成时间选择。原始 Run 和旧摘要保留，服务重启可恢复，清空后的新时间线不会读取旧摘要。此来源检查不等于新增了管理员任意轮次回退 UI。

摘要使用原子文件替换写入，检查与写入之间没有 await；适用于现有单 worker dev，不宣称支持多进程并发提交。

2026-09-16 可见性修正：调试输出记录 N02 的摘要额度和降级标识、N05 的压缩前后用量及后台失败代码。空闲页面根据已发布摘要更新预算环，不再一直显示压缩前的旧请求用量。N04 以本次规划目标校验，70% 不可达时不再阻止整个工作流进入生成节点。

Console 的模型请求记录增加 `purpose`，显示“主回复”或“后台压缩”。摘要请求与主 Run 关联，但使用独立调用计数，并按实际创建时间排序。最终摘要可在版本文件或后续主请求的 context_summary 中查看。节点日志记录 N01 至 N05 的执行顺序，成功日志包含覆盖轮数和压缩前后估算，不打印对话正文或凭据。

## 验证

自动化用受控模型覆盖阈值、节点顺序、多批合并、连续压缩、无效输出、完整工具链、静默并发、停止、重置迟到结果、重启恢复及账号隔离。

2026-09-16 使用本地已配置模型进行一次合成中文对话实测（未使用真实用户历史）：14 个完整轮次，总估算占用从 123.95% 降至 59.88%；摘要 906 字节，上限 3532 字节。摘要保留称呼、生日、咖啡偏好、居住地更正、周六改周日、尚未购票和禁止代发消息等信息。该单次样本用于确认接入和观察效果，不代表长期反复压缩无损。

## Dev 主动压缩入口

Dev 工具箱提供“主动压缩上下文”，调用 `POST /api/chat/context/compact`。仅开发环境管理员可整理自己的已提交历史；主动触发跳过 90% 阈值，仍执行 N01–N05、预算校验和时间线提交检查。复用同账号已有压缩任务，不重复发起模型请求。不删除原文、不创建聊天消息。

按钮等待期间显示“正在整理上下文…”，成功展示压后用量，圆环通过现有会话轮询更新。无新增历史、正在回复/清空、生成失败或清空导致结果失效时显示错误并允许重试。客户端断开不取消后台任务，清空上下文仍会取消该任务。低于阈值并不保证一定可压缩：结果仍必须满足规划目标且占用严格下降。
